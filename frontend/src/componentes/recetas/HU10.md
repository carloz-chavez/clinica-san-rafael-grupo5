# Integración de HU10 con G1 y HU02

`ModalAnulacion` es un componente independiente. El padre proporciona:

- `abierto`, `alCerrar()` para controlar la apertura y cierre del diálogo nativo.
- `usuario`: `id_usuario`, `rol`, `id_medico`.
- `consulta`: `id_consulta`, `id_paciente`, `id_medico`, `anulada`.
- `cliente.anular(idConsulta, { motivo_anulacion })`, o `token` y `baseUrl` para el cliente incluido.
- `alAnular(resultado)` para actualizar la consulta seleccionada, mostrar su estado y deshabilitar el registro de C5. El modal impide repetir la escritura aunque el padre todavía no haya actualizado la consulta.

El cliente no guarda tokens ni datos clínicos, no reintenta escrituras y conserva `estado`, `codigo` y `campos` de los errores de API. Un error de red puede corresponder a una operación confirmada: el usuario puede volver a consultar el estado mediante HU02 antes de reintentar. Un 409 `CONSULTA_ANULADA` bloquea nuevos envíos desde el modal.

## Contrato HTTP

`POST /consultas/{id_consulta}/anular`, sesión de médico responsable (misma política de C5). Admisión, administrador y otros médicos reciben 403. No se concede un permiso administrativo nuevo.

Entrada: `{ "motivo_anulacion": "Corrección ficticia" }`. Obligatorio, sin espacios exteriores, de 1 a 200 caracteres; se rechazan campos adicionales.

Respuesta 200: `id_consulta`, `anulada`, `motivo_anulacion`, `fecha_anulacion`, `id_usuario_anulacion`. La fecha y el usuario los determina el backend. No se cambian ni eliminan datos clínicos, recetas, indicaciones ni citas. Los errores usan el formato de `CONVENCIONES.md`: 401 sin sesión, 403 sin permiso, 404 consulta inexistente, 409 ya anulada, 422 entrada inválida.

El servicio usa `publico.obtener_contexto_consulta` y su bloqueo `FOR UPDATE`, compartido con C5. El bloqueo, la actualización de metadatos y el evento `ANULACION / CONSULTA_MEDICA` viven en la misma transacción de la solicitud. El motivo queda en la consulta y no se copia a la bitácora.

## Pruebas

Backend: desde `backend`, `python -m pytest`. Integración requiere `C3_BASE_DATOS_QA` apuntando a una base **QA exclusiva** llamada `clinica_c3_qa`, inicializada con `db/01_esquema.sql` y `db/02_permisos.sql`. La prueba concurrente requiere además permiso `CREATEDB`: crea una base `clinica_c6_qa_<uuid>` en ese servidor y la elimina al terminar. No utiliza la conexión de desarrollo.

Frontend: desde la raíz, `node --test frontend/pruebas/*.prueba.mjs`. Para incluir la interacción del modal, instalar `react@19`, `react-dom@19`, `jsdom@26` y `esbuild@0.25` en una carpeta temporal QA y definir `C6_UI_QA` con su ruta absoluta. Sin esa variable solo se omite la prueba del modal; las pruebas del cliente API siguen ejecutándose. JSDOM simula la API nativa del diálogo; esta suite no verifica su presentación visual en navegador.
